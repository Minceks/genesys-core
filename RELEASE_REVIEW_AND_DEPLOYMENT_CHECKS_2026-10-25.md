# Publishing review and post-deployment checks

Publishing now reads server-owned release evidence for the exact project, checkpoint and commit. Evidence is retained independently of the one-day job cleanup. Failed/incomplete verification and major screenshot findings block publishing. Missing visual review remains unreviewed and requires the owner's desktop/phone inspection. Deferred integrations and verification limitations are shown explicitly and require separate acknowledgements. These acknowledgements do not mark integrations complete.

The client loads `/publish/review` using the existing signed publishing approval and authenticated project session. `/publish` checks the current review hash and exact acknowledgement IDs before accessing the workspace. Client-supplied verification results and the former generic checkbox cannot bypass the gate. Changing versions resets acknowledgement state, and stale review responses require a fresh review. The export also rechecks its immutable snapshot proof before activation. Existing preview availability is unaffected. Legacy versions without saved release evidence require fresh verification; publishing feature flags remain unchanged.

The publishing review opens in a dedicated native dialog with bounded phone width, scrolling content, keyboard focus containment, Escape dismissal and a visible close action. Deferred items and all acknowledgement groups are visible in this review instead of being compressed into the builder's short settings scroller. Desktop/phone audits cover opening, Escape, reopening, blocking findings, acknowledgement requirements, closing and returning to the composer.

The backend automatically samples up to two active completed previews after deployment. It waits for its deployment ID to appear at the public health endpoint, then fetches real public HTML, checks up to sixteen referenced local scripts/styles/icons with status and MIME validation, and opens each site in fresh desktop and phone Chromium contexts. Missing assets, HTML substituted for JavaScript, blank rendering and runtime errors fail the check. Redirects and arbitrary external asset destinations are not followed by the HTTP probe.

Browser probes use empty sessions and block write requests, service workers and WebSockets. Only same-origin reads and a small asset-CDN allowlist are permitted; external integrations are not exercised. No forms are submitted, reservations created or paid model calls made. These are availability/rendering checks, not aesthetic, functional or security certification. Disabled/deleted previews are excluded. This is a bounded sample, not an exhaustive check of all projects or routes.

Router and frontend startup hooks wait for their own public deployment IDs and notify the backend using `GENESYS_DEPLOY_SMOKE_KEY`. This is a dedicated server-only trigger key; it provides no account or project-write access and never uses a `VITE_` variable. `GENESYS_SMOKE_BACKEND_URL` is configured on all three services, and `GENESYS_SMOKE_FRONTEND_URL` on the frontend. `GENESYS_DEPLOY_SMOKE_ENABLED=0` disables automatic checks and trigger requests. Triggers are deduplicated/coalesced; failures do not endlessly requeue themselves.

Latest detailed results are atomically retained at `/data/deployment-smoke/latest.json` and available through the authenticated internal `/internal/deployment-smoke` endpoint. Public `/health` includes only status/counts/time, without project origins. Failed checks are logged at error level. Checks do not automatically roll back deployments or restart services.
