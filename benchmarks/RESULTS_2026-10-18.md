# Fresh builder audit — 2026-10-18

Four new synthetic applications ran sequentially through the actual orchestrator,
using pinned `gpt-5-mini` behind the benchmark spend guard. These are not fixture
generation results or a comparison of the production Groq/Gemini configuration.
Fixed requests live in `fresh.py`; all four used the same builder revision before
the subsequent improvements. No real payments, customer data or messages were used.

Offline rendering of the exported production bundles found no runtime errors.
Homepage layout checks passed at 1440 and 390 pixels for the store, booking and
dashboard; portfolio passed desktop and failed phone. Objective layout checks do
not establish subjective design quality or complete workflow correctness.

An independent reviewed Playwright check then exercised the store at both widths:
three products/specifications/illustrations, detail navigation and reload, selected
quantity, line/total arithmetic, cart reload and real new-tab persistence, persistent
removal, required/email validation, stored pending local order and cart clearing.
Those checks passed without model calls. The original automatic failure is retained.
Booking/dashboard functionality remains unverified by this audit; do not infer a
pass from compilation or screenshots.

Visual inspection found tiny store product art and a narrow desktop composition,
portfolio phone overflow with auto-width flex children, weak generic artwork in
some sections, and overly narrow dashboard task text caused by broad input sizing.
Booking's public first screen was better composed, but its workflow still needs
complete behavioral verification. Native confirmation dialogs in booking/dashboard
also conflict with the current verifier's supported in-page workflows.

Subsequent builder changes:

- Add exact `newTabText` assertions for badges/visible text, keeping `newTabValue`
  exclusive to form values; reject button-value assertions before executing a plan.
- Include overflowing ancestor and parent geometry in rendered evidence, with
  guidance to fix intrinsic container sizing rather than repeatedly patch children.
- Strengthen instructions for substantial imagery, explicit page widths, flexible
  grid/SVG sizing, checkbox dimensions, usable task text and in-page confirmations.
- Ask for complete stylesheet/import/branding work before declaring a build ready.
- Count repair events independently of the final result's optional `selfHealing`
  field. The store's original metric reported zero despite an observed repair;
  use its raw log rather than that old metric for repair analysis.

Focused regression tests passed. These changes have not been measured with a
second paid four-build suite, so no improved generation success rate is claimed.
The remaining omitted-coverage failures are not waived or relabeled as passes.

Follow-up offline workflow audit: the dashboard passed creation, required-title
validation, keyboard typing, editing, completion/filtering, reload/new-tab
persistence, cancellation of deletion and confirmed deletion/reload at both widths.
Only newly created synthetic records were deleted; all three sample tasks remained.
Booking validation, creation, confirmation, persistence and cancellation also
passed with programmatic filling, but ordinary typing failed at both widths:
the nested `BookingForm` component remounted after each character. The booking
app therefore remains failed overall. A label in the dashboard also includes its
validation error in its accessible name; reviewed selectors used its stable Title
prefix, and no accessibility-quality pass is claimed.

`python -m benchmarks.review_workflows .verification-evidence/fresh-builds-20261018-a`
reproduces those reviewed, offline checks. It supports only these known synthetic
artifacts. Its exact native-confirm handling is local to the reviewed test records;
it does not enable automatic acceptance of arbitrary dialogs in the builder.
The builder subsequently gained a React component-identity preflight and real
keyboard `type` actions to catch the demonstrated focus-loss defect. No new paid
model requests were needed for this follow-up.
