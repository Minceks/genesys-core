# General generated-product design quality

The manually reviewed Civic Prepared storefront is an individual project. Its polish was not evidence that every future generation would receive the same treatment. This change strengthens the shared builder rather than applying that storefront's theme to other products.

`agent/design_quality.py` defines a shared quality contract for business sites, commerce, portfolios, booking, dashboards, editorial, documentation, task applications and games. Each has a different visual focus. Six common criteria cover identity, supporting content, typography/alignment, subject-matched assets, interaction finish and phone composition. Minimal and text-led requests remain valid; premium does not require luxury styling, extra pages or decorative animation.

The contract enters each refreshed design execution brief, the actual build-specification planning request and screenshot-review context. Existing targeted edits retain their product identity, visual system, behavior and data scope. The same criteria guide implementation and review instead of relying on commerce-specific instructions.

Previously the vision reviewer received only the opening desktop and phone viewports, even though separate full-page PNGs were retained. It now receives two bounded, labeled contact sheets, each sampling up to three real viewport positions on the current page. Supporting content can therefore be judged without shrinking an entire long page into a thumbnail. Captures wait briefly for visible image decoding, use an isolated browser context for in-memory image composition and restore the app's viewport/scroll position. No controls are clicked or routes selected. Very short pages produce one panel. Metadata records the actual sampled offsets, and the reviewer is told not to claim unseen routes or interactions were reviewed.

The existing maximum of two visual-model requests per build remains: one review/polish opportunity and one recheck. There are still two generated images and at most two reference images, with the existing two-megabyte limit per image and model budget reservation. Contact sheets contain more image area, so identical request counts do not guarantee identical token costs. Provider failure remains unavailable, never an aesthetic approval. Layout, functional verification and subjective visual judgment remain separate.

Validation: 108 tests passed across purpose-aware criteria, actual planning payloads, real Chromium contact-sheet pixels and scroll restoration, integrated desktop/phone review delivery, visual review, composition, visual system, specification recovery, experience blueprints, evidence storage, design foundations, verification reports and browser lifecycle. The pixel test confirms supporting work and a case study appear in later panels, rather than merely asserting that screenshot methods were called. No paid generation or vision calls were made by these tests.

A read-only browser check against the existing public preview also produced three panels per viewport: desktop offsets 0/800/1600 and phone offsets 0/844/2264. The sheets are approximately 149 KB and 84 KB. Evidence is in `.verification-evidence/general-design-20261024/`, with screenshot hashes and actual offsets in `public-capture.json`. This validates capture delivery on a real deployed product; it is not a fresh AI generation or an aesthetic approval.

This is a shared generation/review improvement, not proof that new model output has achieved a premium aesthetic. Fresh generated products still need evaluation against the criteria. Existing projects are not silently regenerated. Captures sample the current page; they do not automatically exercise all inner routes or simulate application states.
